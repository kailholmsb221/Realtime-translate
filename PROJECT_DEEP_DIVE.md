## 1. Что это за проект

**Realtime Translator** — локальная надстройка над Zoom/Meet, которая делает синхронный перевод в двух направлениях одновременно:

| Поток | Откуда звук | Что происходит | Куда уходит результат |
|---|---|---|---|
| `in` («Собеседник») | WASAPI loopback — то, что Zoom играет вам | en/kk → ru | наушники + субтитры |
| `out` («Вы») | физический микрофон | ru → en/kk | VB-Audio Virtual Cable → Zoom слышит ваш переведённый голос |

Фишка: перевод озвучивается **голосом говорящего** — ваш голос клонируется заранее по 15–30-секундному сэмплу, голос собеседника движок клонирует сам за первые ~12 секунд разговора.

Всё локально, 0 ₽, только open-source веса. Целевая задержка «конец фразы → звук перевода» ≤ 2.5 с на RTX 4050 (6 GB).

## 3. Архитектура

```
             +------------ Zoom ------------+
             |                              |
   WASAPI loopback                    CABLE Output (микрофон Zoom)
             |                              ^
             v                              |
     +---------------+              +---------------+
     |  pipeline IN  |              | pipeline OUT  |
     +-------+-------+              +-------+-------+
             |                              |
     Silero VAD -> режет на фразы по паузам |  (то же самое)
             v                              |
     faster-whisper small int8  (GPU ~1 GB) |
             |  stt.partial / stt.final     |
             v                              |
     NLLB-200-600M  (CPU, int8)             |
             |  translation.ready           |
             v                              |
     XTTS-v2 (GPU ~2.5 GB) / MMS-TTS kaz    |
             |  PCM 24 kHz стримом          |
             v                              v
        наушники                       CABLE Input

        ----------- EventBus -----------> WebSocket :8765 --> Next.js UI
                    |                     REST :8766      --> история
                    +--> SQLite (utterances, sessions, voices)
```

### Ключевые инженерные решения

**Контракты как источник правды.** Все события — конверт `{type, ts, payload}`, описанный JSON Schema draft 2020-12 в `engine/contracts/`. Каждый конверт валидируется **дважды** — общей схемой `envelope.json` и схемой своего типа — и **на отправке, и на приёме**. Python-сторона: `to_json()` не выпустит невалидное событие в сокет; TypeScript-сторона: `parseEnvelope()` отбрасывает мусор и считает его в `invalidCount`. Это редкость — обычно валидируют в одну сторону.

**Развязка STT от MT/TTS.** Главное решение для латентности. В `pipeline.py` распознавание **никогда** не ждёт перевод и синтез:

```
источник -> SttEngine.run -> stt.* в шину
                 +- stt.final -> asyncio.Queue -> один фоновый воркер:
                        INSERT utterances -> перевод -> TTS -> метрики
```

Один воркер на конвейер, строго FIFO — поэтому `translation.ready` приходят в том же порядке, что и `stt.final`, и UI может привязывать перевод к реплике по порядку. Пока воркер синтезирует фразу №1, whisper уже распознаёт фразу №2.

**Ленивые импорты — везде.** `torch`, `faster_whisper`, `TTS`, `transformers` импортируются **внутри методов**, а не на уровне модуля. Поэтому весь движок импортируется на машине без единой модели, и 292 теста бегут за 9 секунд.

**Фабрики + протоколы вместо наследования.** `Runtime.create()` — единственное место, где решается «модели или заглушки». Дальше конвейер видит только `Transcriber`, `TranslationProvider`, `TtsProvider`, `AudioSource`/`AudioSink`.

**Изоляция состояния.** Модели — синглтоны на процесс (XTTS кэшируется по ключу `(каталог, устройство)` под `threading.Lock` — 2.5 GB VRAM второй раз не выделяются). А состояние, привязанное к потоку — VAD, таймлайн, окно контекста — создаётся **своё на каждый конвейер**.

**Backpressure вместо обрыва.** `EventBus` при переполнении очереди подписчика выбрасывает **самое старое** событие и растит счётчик `dropped` — конвейер важнее полноты ленты субтитров. Аудио-sink ждёт до 2 с места в буфере, потом отбрасывает чанк.

## 4. Модели: что используется и как оно обучено

**Важно сразу:** проект **не обучает и не дообучает ничего**. Ни одной строки тренировочного кода в репозитории нет — это чистый inference-пайплайн поверх четырёх предобученных чужих моделей, соединённых в реальном времени. Всё клонирование голоса — **zero-shot**: веса не трогаются, голос кодируется в вектор-условие.

### 4.1 Silero VAD — разметка речи

Крошечная модель (~2 МБ) — свёрточно-рекуррентный классификатор, который на каждое окно **ровно 512 сэмплов** при 16 kHz выдаёт `P(речь)`. Обучена автором на большом многоязычном корпусе как бинарная классификация «речь / не-речь» с аугментацией шумом.

В проекте обёрнута в `vad_silero.py`: audio_io отдаёт чанки по 30 мс (480 сэмплов), а Silero требует 512 — обёртка копит буфер и нарезает окна сама. `VADIterator` с гистерезисом: `threshold=0.5`, фраза закрывается после `min_silence_duration_ms=500`, вокруг границ добавляется `speech_pad_ms=100`.

### 4.2 faster-whisper `small` — распознавание

**Что за модель.** Whisper от OpenAI — encoder-decoder Transformer, обученный на **680 000 часов** слабо-размеченного многоязычного аудио из интернета (аудио + субтитры, без ручной разметки). `small` = 244M параметров, 12 слоёв энкодера, d_model=768.

**Как он устроен.** Вход — лог-мел-спектрограмма (80 мел-полос, окно 25 мс, шаг 10 мс), **всегда добитая до 30 секунд**. Декодер авторегрессивно порождает BPE-токены, причём в одну последовательность вплетены служебные токены задачи: `<|ru|><|transcribe|><|notimestamps|>`. То есть распознавание, определение языка и перевод-на-английский — одна и та же мультизадачная seq2seq-модель, задача выбирается токеном в промпте.

**Что в проекте.** Не оригинальный PyTorch-whisper, а faster-whisper — реимплементация на **CTranslate2** (движок инференса для Transformer, с собственным графом, слитыми ядрами и квантизацией). Квантизация `int8_float16`: веса хранятся в int8, матричные операции идут в fp16 — примерно x2 по памяти и скорости против fp16 при почти неизменном WER. Ровно ~1 GB VRAM.

Параметры декодирования выбраны под латентность:

```python
beam_size=1                      # greedy, самый быстрый режим
vad_filter=False                 # VAD уже отработал выше по конвейеру
condition_on_previous_text=False # не кормим модели её же прошлый вывод
temperature=0
```

`condition_on_previous_text=False` — правильное решение: именно эта опция в потоковом режиме вызывает у whisper «залипание» (модель начинает повторять предыдущую фразу).

Для казахского предусмотрена подмена на файнтюн (`RT_STT_KK_MODEL`, например ISSAI whisper-kk) — whisper `small` казахский знает плохо.

### 4.3 NLLB-200-distilled-600M — перевод

**Что за модель.** *No Language Left Behind* от Meta — encoder-decoder Transformer на **200 языков**, включая казахский. Обучение: параллельные корпуса, добытые **автоматическим майнингом** из веба (сопоставление предложений по близости в многоязычном эмбеддинг-пространстве LASER3), плюс обратный перевод, плюс curriculum-расписание по объёму данных для редких языков. Версия `distilled-600M` — дистилляция большой MoE-модели (54B) в плотную 600M: студент учится воспроизводить распределение учителя.

**Как задаётся направление.** У NLLB нет отдельных моделей на пару языков. Исходный язык задаётся через `tokenizer.src_lang`, целевой — **принудительным первым токеном декодера**:

```python
tokenizer.src_lang = "rus_Cyrl"
model.generate(..., forced_bos_token_id=tokenizer.convert_tokens_to_ids("kaz_Cyrl"))
```

Коды — из FLORES-200: `rus_Cyrl`, `eng_Latn`, `kaz_Cyrl`. Токенизатор — SentencePiece.

**Что в проекте.** `nllb.py`: CPU (GPU целиком отдана STT и TTS), `num_beams=1`, `max_new_tokens=128`, плюс **динамическая квантизация** Linear-слоёв в int8 (`quantize_dynamic`) — примерно x1.5–2 на CPU. Сверху LRU-кэш на 256 переводов и короткие замыкания: пустая строка и `src == dst` до модели не доходят.

Ограничение честно записано в коде: NLLB переводит **пофразно, без контекста диалога**. Окно из 3 последних фраз в `TranslationService` есть, но `NllbProvider.translate()` делает `del context` — оно заготовлено под будущего LLM-провайдера.

### 4.4 XTTS-v2 — синтез с клонированием голоса

**Что за модель.** Coqui XTTS-v2, ~16 языков, синтез на 24 kHz. Конвейер из трёх частей:

1. **Кондиционирование.** Референсный WAV (6–30 с) → мел-спектрограмма → Perceiver-подобный ресемплер даёт `gpt_cond_latent`, плюс speaker-encoder даёт `speaker_embedding`. Это и есть «отпечаток голоса» — тембр, темп, манера.
2. **Авторегрессивный GPT.** Декодер в стиле GPT-2 принимает текстовые токены + оба латента и порождает **дискретные аудио-токены** — коды VQ-VAE, обученного квантовать мел-спектрограмму в словарь.
3. **Вокодер.** Декодер семейства HiFi-GAN разворачивает коды в waveform 24 kHz.

**Почему это zero-shot.** Голос не «дообучается» — он **кодируется в два тензора** за один проход. Никаких градиентов, никакого файнтюна. Поэтому клон собеседника готов через ~12 секунд его речи, а не через часы обучения.

**Что в проекте.** `xtts.py`:
- латенты считаются **один раз** и кешируются на диск (`<voices_dir>/<voice_id>/latents.pt`);
- используется **`inference_stream`** — модель отдаёт аудио кусками по мере генерации. Это принципиально для латентности: в метрику идёт время **до первого чанка**, а не время синтеза всей фразы;
- `inference_stream` — блокирующий генератор, поэтому он крутится в `asyncio.to_thread`, а чанки едут в корутину через `asyncio.Queue(maxsize=8)`. Есть `threading.Event` для остановки, поток инференса не подвиснет, если потребитель ушёл.

Без `voice_id` берётся встроенный голос из `speakers_xtts.pth` (по умолчанию «Ana Florence»).

### 4.5 MMS-TTS-kaz — казахский без клона

Meta *Massively Multilingual Speech*: по одной монолингвальной модели на язык, архитектура **VITS** — условный вариационный автоэнкодер с нормализующим потоком и состязательным обучением, генерирующий waveform напрямую из текста (end-to-end, без отдельного вокодера). Обучены эти модели на записях чтения религиозных текстов (Новый Завет) — отсюда характерная «дикторская» просодия. Один голос, клонирования нет, ~150 МБ, CPU.

Поэтому в проекте: **для kk клона голоса нет**, `voice_id` роутером игнорируется, автоклон не создаётся.

## 5. Научный разбор: почему задержка именно такая

### Система работает «по рации», и это осознанный выбор

Здесь **не потоковое распознавание**. Применён классический **VAD-эндпоинтинг**: движок ждёт паузу, и только потом отдаёт whisper фразу целиком. Отсюда цепочка:

```
речь кончилась
   -> +500 мс           VAD должен УБЕДИТЬСЯ, что это пауза (min_silence_ms)
   -> + STT             whisper прогоняет всю фразу (30-с окно, greedy)
   -> + MT              NLLB на CPU, beam=1
   -> + TTS до 1-го чанка   XTTS inference_stream
   -> звук в наушниках
```

**Бюджет 2.5 с считается от конца фразы** — то есть `min_silence_ms` в него **не входит**. Реально воспринимаемая задержка ≈ `total_ms + 500 мс`. В README это оговорено, но в UI индикатор подсвечивает порог 2500 именно по `total_ms`, так что он оптимистичнее ощущений на полсекунды.

Альтернатива — **симультанный перевод** с политикой вроде wait-*k* (переводить, не дожидаясь конца фразы, с фиксированным отставанием в *k* слов) плюс streaming-ASR. Это дало бы задержку в сотни миллисекунд, но требует другой модели перевода и обработки ревизий гипотез. Для MVP выбор правильный — но разговор будет полудуплексным.

### Приёмы, которые реально срезают латентность

1. **`beam_size=1` и `num_beams=1` везде.** Greedy вместо beam search — x2–3 быстрее ценой небольшой потери качества.
2. **Стриминговый TTS.** `tts_ms` меряется до **первого** чанка. Фраза на 3 секунды звучания начинает играть через ~300–500 мс, а не через 1.5 с.
3. **Квантизация на обоих концах.** int8_float16 на GPU, dynamic int8 на CPU.
4. **Prewarm при старте.** Модели грузятся в порядке whisper → XTTS → NLLB (важно: XTTS должен вставать на уже занятую whisper память), время и VRAM каждого шага в логе.
5. **Preroll 300 мс.** VAD сообщает о начале речи с задержкой `min_speech_ms`, поэтому `_RunState` держит кольцевой хвост потока и прихватывает аудио «до» момента `speech_start` — иначе whisper терял бы первый слог.
6. **Принудительное закрытие фразы** через `max_utterance_ms=15000`.
7. **LRU-кэш переводов** — повторы («да», «окей», «понял») бесплатны.

## 6. Качество кода — что сделано хорошо

- **Типизация.** `mypy --strict` чист на 56 файлах. `Final`, `Literal`, `StrEnum`, `frozen dataclass` + `slots` — везде.
- **Тесты.** 292 python + 78 TS. Все на фейках, без моделей и без звуковой карты. Тесты с реальными весами помечены `@pytest.mark.real_models`.
- **Комментарии объясняют «почему», а не «что».** Пример из `state.ts`: «Искать с конца нельзя: перевод и синтез идут дольше распознавания, и к моменту `translation.ready` в ленте уже лежат более свежие `stt.final`».
- **Обработка ошибок продумана по слоям.** Падение синтеза теряет **одну фразу**, а не сессию. Падение рассылки в WebSocket логируется, но не убивает цикл. Падение источника явно ловится, иначе задача конвейера тихо умерла бы, а движок считал бы сессию живой.
- **Правовая гигиена.** Голос трактуется как биометрия: автоклон собеседника по умолчанию **удаляется вместе с сессией**. Лицензии (XTTS — CPML, NLLB и MMS — CC-BY-NC) разобраны с прямым выводом: **сборка для личного и исследовательского использования, не для продукта**.

## 7. Код-ревью: находки

### 1. Цифровая петля обратной связи в дефолтной конфигурации (критично)

**Файлы:** `engine/audio_io/config.py:107-109`, `engine/audio_io/windows.py:595-599`, `engine/audio_io/devices.py:306`

По умолчанию `loopback_name = None` → берётся loopback **устройства вывода по умолчанию**. И `headphones_name = None` → перевод собеседника играет **в то же самое устройство вывода по умолчанию**. Это один и тот же эндпоинт.

WASAPI loopback снимает render-поток устройства **цифрово**. Значит русский перевод, который движок только что синтезировал и отправил в наушники, тут же возвращается во входной поток конвейера `in`, уходит в whisper с `language="en"`, даёт мусорный текст, переводится обратно и озвучивается снова — самоподдерживающийся цикл.

README говорит «нужны наушники, иначе loopback поймает собственный перевод». Это **неверная диагностика**: наушники спасают только от *акустической* петли через микрофон (путь `out`). От *цифрового* захвата собственного TTS наушники не спасают.

Решение: развести устройства — Zoom играет во второй виртуальный кабель, движок снимает loopback с него и играет перевод в физические наушники (`RT_AUDIO_LOOPBACK` + `RT_AUDIO_HEADPHONES` на разные устройства). Либо гейтить захват `in`, пока играет TTS.

### 2. Тест декодирует stderr в кодировке локали — падает на русской Windows

**Файл:** `engine/tests/test_e2e_file_mode.py:45-52`

```python
subprocess.run([...], capture_output=True, text=True, timeout=TIMEOUT_S)
```

`text=True` без `encoding` берёт кодировку локали (cp1251), а дочерний процесс пишет UTF-8:

```
AssertionError: assert 'не найден' in 'С„Р°Р№Р» РЅРµ РЅР°Р№РґРµРЅ: ...'
```

Фикс на одну строку: `encoding="utf-8", errors="replace"` — или `env["PYTHONUTF8"] = "1"` рядом с уже проставляемым `env["LOG_LEVEL"]`.

### 3. Незакрытая partial-гипотеза блокирует финальное распознавание

**Файл:** `engine/stt/engine.py:230-238`

```python
state.trim_to(event.ts_ms)
if pending is not None:
    ready = await self._collect(pending)   # <- ЖДЁМ ненужную гипотезу
    ...
final = await self._final_event(state, stream_enum, target_lang)
```

Финал встаёт в очередь за промежуточной гипотезой, которая через миллисекунду станет неактуальной. Это уходит **прямо в критический путь** бюджета 2.5 с: +100–400 мс на реальной GPU, больше на CPU. `partial_interval_ms=1000`, так что вероятность попасть в такое окно высока.

Фикс: `pending.cancel()` вместо `await self._collect(pending)`.

### 4. Глобальный лок сериализует оба направления перевода

**Файл:** `engine/translate/nllb.py:171-192`

`_generate()` держит `self._lock` на **весь** инференс, потому что `tokenizer.src_lang` — мутабельное состояние. Но провайдер **один на процесс** и общий для обоих конвейеров: перевод вашей реплики ru→en блокирует перевод реплики собеседника en→ru.

Фикс: не мутировать состояние токенизатора, а передавать `src_lang` в вызов, и оставить лок только вокруг `model.generate`.

### 5. `temperature=0` отключает штатную защиту whisper от зацикливания

**Файл:** `engine/stt/whisper_fw.py:151-158`

Whisper по умолчанию делает temperature fallback (`0.0 → 0.2 → 0.4 → …`) при срабатывании `compression_ratio_threshold` / `log_prob_threshold` — это механизм выхода из декодерных петель («…спасибо спасибо спасибо»). Передан скаляр `temperature=0`, fallback выключен. Также не заданы `no_speech_threshold` и `hallucination_silence_threshold`.

### 6. WebSocket :8765 не проверяет Origin

**Файл:** `engine/orchestrator/server.py:346-348`

```python
self._ws_server = await websockets.serve(self._handle_client, host, port)
```

Параметр `origins` не передан. WebSocket **не подчиняется CORS**, поэтому любая веб-страница в браузере пользователя может сделать `new WebSocket("ws://127.0.0.1:8765")` и:

- получать **весь живой транскрипт разговора**;
- отправлять `session.start` / `session.stop`.

REST на 8766 прикрыт CORS-мидлварью — а WS, через который течёт содержимое разговора, открыт. Фикс: `origins=[config.cors_origin]` в `websockets.serve`, либо токен в query.

### 7. Мелочи

- **`torch.quantization.quantize_dynamic`** (`nllb.py:167`) — API переехал в `torch.ao.quantization`. В связке с `filterwarnings = ["error::DeprecationWarning:engine.*"]` это однажды уронит тесты `real_models`.
- **`mypy` с `python_version = "3.11"`** падает на стабах свежего numpy — окруженческое, не код: с `--python-version 3.14` всё чисто.
- **`ruff format --check`** на ruff 0.16 хочет переформатировать 4 README.md. Стоит зафиксировать версию ruff в `requirements-dev.txt`.
- **`total_ms` в UI.** Порог 2500 подсвечивается по метрике, которая не включает `min_silence_ms`.

## 9. Итог

Проект зрелый: контракты валидируются с двух сторон, типы строгие, тесты идут без железа, ошибки локализованы по фразам, правовая и лицензионная стороны разобраны честно. Модели — четыре чужие предобученные сети, соединённые в конвейер; собственного обучения нет, клонирование голоса zero-shot через латенты XTTS.

Из находок чинить стоит две: **цифровую петлю loopback→наушники** и **ожидание partial перед final**. Остальное — гигиена: кодировка в тесте, Origin на WebSocket, лок вокруг NLLB, temperature fallback у whisper.
